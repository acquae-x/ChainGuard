# ChainGuard 工业级成熟度评估（2026-07-12，Phase 3 关闭后）

评估基准：一个部署在制造企业内网、供 10–200 人使用的关键业务辅助决策系统。逐维度评级：✅ 达标 / 🟡 基本达标（有条件或有小缺口）/ ❌ 缺口。

## 1. 可用性与容错

| 项 | 评级 | 说明 |
|---|---|---|
| 断电/宿主机重启自恢复 | ✅ | 全部常驻服务 `restart: unless-stopped`，migrate 正确设 `no` |
| 后端进程级容错 | ✅ | uvicorn 4 worker；决策/导入作业双线程池分离（死锁已修）+ 60s 超时 + 幂等键 |
| 外部依赖降级 | ✅ | LLM：缺 key/断网/超时 → 3 次退避重试 → Mock 兜底；Webhook：失败返回 False 不抛异常；prometheus_client 缺失 → 内存计数 |
| 前端对后端不可用的感知 | 🟡 | 502/503/504 与网络错误 → 黄条降级 + mock 兜底，已实测；**缺口：DB 断连时后端返回 500（CG-5000），前端不识别为"后端不可用"**，用户只看到零散报错。正解：后端把依赖类故障（DB 断连）返回 503，与代码缺陷（500）区分 |
| 单点架构 | 🟡 | 单机 compose，无 HA——该规模下可接受，但需在文档明示 RTO 依赖人工重启/恢复 |

## 2. 数据可靠性

| 项 | 评级 | 说明 |
|---|---|---|
| 数据库持久化与备份 | ✅ | Postgres 命名卷 + 每日 02:00 pg_dump（保留 7 天），恢复命令已文档化并实测过手动触发 |
| RPO/RTO 声明 | 🟡 | 每日备份意味着最坏丢 24h 数据（RPO=24h）。企业若不可接受，需 WAL 归档/更高频备份——应在部署文档明示让客户知情选择 |
| appdata 卷不在备份范围 | ❌ | 决策引擎审计 jsonl、经验卡存 appdata 卷，pg_dump 不覆盖，宿主机丢失即丢失。短期：备份脚本加 tar appdata；长期正解：引擎审计统一入库（与 webapi 审计合流） |
| 迁移体系 | ✅ | Alembic 显式迁移，up/down 与真实 Postgres 均实测；有防回归测试 |

## 3. 离线与无外网运行

| 项 | 评级 | 说明 |
|---|---|---|
| 运行时零外网依赖 | ✅ | 前端产物无 CDN 引用（antd/图表全打包）；LLM/Webhook 均可关可降级；容器健康检查走内网 |
| 构建/部署需外网 | ❌ | 首次部署要拉基础镜像 + pip/npm（本次实测就被墙卡住）。**离线部署路径缺失**：需提供 `docker save` 镜像离线包 + 导入脚本 + 部署文档"离线安装"章节——制造业内网环境这是常态需求，不是加分项 |
| 客户端断网 | ✅ | 黄条 + 显式 mock 降级，不白屏不静默 |

## 4. 安全

| 项 | 评级 | 说明 |
|---|---|---|
| 认证与会话 | ✅ | bcrypt、JWT 双 token、refresh 全 HttpOnly + 轮换、登录限流 5/min |
| 授权 | ✅ | 9 角色权限码前后端统一、租户强制隔离（有测试）、资源域数据权限、字段级脱敏 |
| 已知残余 | 🟡 | refresh token 无服务端吊销（D2 已登记）；.env 明文机密（该规模可接受，文档应建议文件权限）；演示痕迹泄漏（B 组：Demo@1234 提示、租户名联想） |
| 传输加密 | ❌ | compose 只出 8080 明文 HTTP。内网亦应支持 TLS：文档需给反代 TLS 方案（nginx 证书挂载或 Caddy），并联动 `REFRESH_COOKIE_SECURE=true` |
| 错误信息防泄漏 | ✅ | 统一信封，500 不带内部细节，有测试锁定 |

## 5. 可观测性

| 项 | 评级 | 说明 |
|---|---|---|
| 日志 | 🟡 | 结构化 JSON + traceId 贯穿，达标；**缺日志轮转**——compose 未配 json-file max-size，长期运行磁盘会被 docker logs 吃满 |
| 指标 | 🟡 | /metrics（决策计数/延迟/HTTP 层）齐全，但**没有人消费**：无 Prometheus 抓取、无告警。最小闭环：compose 加可选 profile（prometheus+grafana）或文档给抓取配置 + 三条关键告警（决策失败率、作业积压、磁盘水位） |
| 探活 | ✅ | healthz/readyz 分离、免鉴权 liveness、compose healthcheck 内网直连 |

## 6. 性能与容量

| 项 | 评级 | 说明 |
|---|---|---|
| 资源约束 | ❌ | compose 无 mem/cpu limits——失控进程可拖垮宿主机（决策引擎跑 sklearn，内存尖峰真实存在）。至少给 api/postgres 设 limits |
| 容量口径 | 🟡 | 导入有 20MB 上限与流式处理；但无并发容量说明（4 worker × 线程池 4，决策作业吞吐上限约 4 并发）。文档应给容量建议而非让客户猜 |

## 7. 可维护性与工程化

| 项 | 评级 | 说明 |
|---|---|---|
| 测试 | ✅ | 后端 511+（含 27 项 webapi/部署契约）、租户隔离/状态机/错误信封均有锁定测试 |
| CI | 🟡 | 工作流齐备（单仓/双仓两套），但尚未在真实 GitHub 上跑过——待推送验证 |
| 文档 | ✅ | 部署/迁移/集成/SLA 文档齐全；本次验收暴露的小错（healthz URL、手动备份命令）已列改进清单 |
| 变更纪律 | ✅ | 规格→实现→独立评审→实测验收的流程在三个 Phase 里实际执行并抓住了真问题（截断误判除外，双向都有教训） |

## 总评

**当前水位：合格的"内网试点级"（pilot-ready），距"生产级"差六件事**，全部是明确可执行项而非架构返工：

1. 离线部署包与文档（3-❌，制造业刚需）
2. appdata 卷纳入备份 / 引擎审计入库（2-❌）
3. TLS 方案文档化（4-❌）
4. 日志轮转 + 资源限制（5/6-❌，两行 compose 配置的事）
5. DB 故障返回 503 并触发前端降级（1-🟡）
6. 监控告警最小闭环（5-🟡）

架构底子是健康的：降级链路层层有兜底且经过实测（断网黄条、LLM 降级、备份恢复），租户隔离和权限体系有测试锁定，迁移体系真实可用。真正的差距不在健壮性而在 05 清单 C 组——决策数据的真实化，那决定这个系统是"能用"还是"有用"。
