## E. Streamlit 演示版能力核对（2026-07-12 补充）

逐项对照 `ChainGuard/app.py`（11 步决策流 + 高级分析）与 Web 版。关键事实：**辩论/仲裁/约束分析等后端引擎已经在算**（`DecisionResult` 包含 rebuttal、arbitration、debate_result、constraint_analysis、experience_card、explanation、audit_entry），是 Web 侧的作业入库时丢弃了这些字段、前端无页面承接——属"暴露问题"而非"重写引擎"。

### E-1 决策推演深度（Streamlit Step 4–6、8、10：冲突检测/辩论/仲裁/约束驾驶舱/可解释说明）

Web 版现状：完全缺失；审批页"查看完整推演"链接无实质内容。
修法：① 决策作业持久化完整 DecisionResult（jobs.result 或新表 decision_details）；② 新增 `GET /incidents/{id}/decision-detail`；③ 前端"完整推演"页按 Streamlit 四阶段结构渲染：方案评分与冲突 → 辩论过程（rebuttal）→ 仲裁结论与推导 → 约束冲突与推荐调整 → 可解释说明。Pareto 前沿图（27 策略组合）可后置。

### E-2 多格式数据接入（Streamlit 数据接入 Agent：CSV/Excel/PDF/图片 + OCR 三级级联 + 服务器目录批量）

Web 版现状：导入仅支持 csv/xlsx（后端 upload 端点扩展名白名单也只放行这两种）；`ingestion_agent.ingest_files` 的 PDF/图片→LLM 视觉→离线 OCR→文本层级联能力完全未暴露。
修法：upload 白名单扩展 pdf/png/jpg/jpeg（沿用 MAX_IMPORT_BYTES）；导入作业按扩展名分流——csv/xlsx 走现有 streaming_import，pdf/图片走 ingest_files 归一化后再入既有 preflight→execute 流水线；前端导入向导第 1 步文案与 accept 属性同步放开；服务器目录批量导入作为运维脚本保留，不进前端。

### E-3 经验自学习闭环（Step 7、9：经验卡生成 + 历史经验引用 + 参数校准对比）

Web 版现状：案例库页只有 seed 的一张经验卡；决策作业生成的 experience_card 未入库；方案卡的"历史经验引用/置信度调整"未展示；参数校准（数据驱动 vs 专家默认）无入口。
修法：作业完成时把 experience_card 写入 experience_cards 表；方案详情展示 experience_references；参数校准对比放管理端（settings 或报表），低优先。

### E-4 监控与运营面板（Step 1 库存风险计算、敏感性分析、价值仪表盘、系统健康/漂移体检、模型对比评测）

Web 版现状：风险列表来自落库数据而非实时 inventory_monitor 计算；敏感性分析、价值仪表盘（本次收益/累计时间线/决策提速）、漂移体检、6 模型对比均无。
修法：分两档——价值仪表盘接入报表看板（P2 骨架本就预留）；库存风险实时计算依赖 C2（导入数据接入决策链路）后才有意义；敏感性/漂移/模型对比属分析师功能，后置到 Phase 5 末或管理端专区。

### E-5 决策报告导出（Streamlit 下载决策报告 JSON）

Web 版现状：无。修法：decision-detail 页加"导出报告"（JSON 先行，PDF 后置）。

## D 组决策结果（2026-07-12，产品负责人拍板）

- **D1 = 会签前置（2026-07-12 复审细化，三项补充决策已拍板）**：**仅高风险**审批单会签阻塞（中风险>5万维持现状：抄送财务不阻塞）。状态机：boss 批准 → `pending_countersign` → 财务会签 → `approved` 并生成任务。**超时自动放行**：默认 4 小时（`COUNTERSIGN_TIMEOUT_HOURS` 可配）财务未会签 → 自动生效并生成任务，审计标记"超时未会签自动放行"，通知财务事后追认。**拒签=打回**：财务拒绝会签必填理由，审批单置 rejected、事件回 planning，复用现有驳回路径。实现依赖：超时放行需要一个轻量后台定时扫描（可复用作业线程池，每 5 分钟扫一次 pending_countersign），这是系统首个调度器，任务逾期通知（D3）后续复用它。前端审批页展示"待会签/已超时放行"状态。**纳入 Phase 4**（编号 A5）。
- **D2 = 押后 Phase 5**：refresh token 吊销（jti 黑名单）列入 Phase 5 安全加固，与引擎审计入库（F5 长期）同批。
- **D3 = 固定规则版（Phase 5）**：通知订阅采用"规则即数据"设计——`notification_rules` 表（event_type → 接收方解析策略），Phase 5 按下表内置固定规则，后续升级用户自定义订阅时只是对同一张表开放 CRUD，不返工。渠道：站内信 + webhook（B7）；邮件后置。噪音控制：同对象同事件 5 分钟聚合，已读跨端同步。

| 新高风险 / 风险升级 | scm_lead、boss |

## Phase 4 复审注意事项（2026-07-12，实现前必读）

1. **A4 范围明确化**（原表述"接口层"太模糊）：Phase 4 的 impact 只做"尽力而为"版——从事件关联风险的 details 提取物料/供应商名，到 data_records 已导入资料中匹配，返回可得部分；匹配不到的维度返回明确的 `dataMissing: true` 标记，前端展示"数据不足，完善基础资料后可见"而非空表。完整版等 5B 结构化表。
2. **A2 与 A5 改同一段代码，必须一起做**：任务生成逻辑当前在 approve 动作里；A5 会把高风险的任务生成时机移到"会签完成/超时放行"，A2 又给任务加截止时间和真实负责人。两项分开做必然冲突，按 A5 定状态机 → A2 补字段的顺序在同一批改。
3. **A5 会破坏现有测试，要求显式更新而非绕过**：test_webapi 的审批链测试（高风险 approve→5 任务）在会签前置后语义变化，必须改为"approve→pending_countersign→会签→任务生成"+新增超时放行/拒签打回用例；禁止把断言改弱糊弄过去。A5 通知只做最小集（会签请求已有，新增超时放行提醒 finance），完整规则表等 5B 的 D3。
4. **A1 先于 E-2**：A1 统一 csv/xlsx 的校验口径（预览直接消费后端 preflight），E-2 在统一后的管线上扩 pdf/图片分流。反过来做会返工。
5. **E-2 验收场景要现实化**：图片抽取依赖 OCR 级联（LLM 视觉需 QWEN key、离线 OCR 需 tesseract），验收机器两者都可能没有。验收标准定为三选一：配了 QWEN key 时图片成功归一化落库；或装了 tesseract 时同上；或两者皆无时图片落入 staging 并明确标记"待人工处理"（不许静默失败）——第三种也算通过，因为降级行为正确。

### Phase 5 复审发现的风险与红线（实现前必读）

1. **引擎输入契约未文档化**：context schema 只存在于 demo JSON；5B 规格第一件事是把它写成正式 schema。且 thresholds/权重/收益口径全按 demo 量级调校，真实数据接入后必须重校准——校准工作量计入 5B，不是"换个数据源"。
2. **多租户 vs 引擎全局态**：权重、经验卡（experience_cards.json+TF-IDF 索引）、历史管线均为全局单份。5B 必须租户级隔离（经验卡跨租户泄漏=商业机密事故）；租户级配置的存放（DB/每租户文件）需在规格中决策。
