# ChainGuard 3分钟答辩演示脚本

## 0:00-0:20 打开页面

操作：

```powershell
cd /d D:\github_projects\Chainguard\ChainGuard
streamlit run app.py
```

打开浏览器中的 Streamlit 页面。

讲解：

“各位评委好，这是 ChainGuard 供应链应急响应系统。它面向供应链中断场景，核心目标是在库存风险真正造成延期前，提前触发应急决策，并通过多 Agent 协同、辩论仲裁和经验沉淀形成闭环。”

## 0:20-0:35 点击运行完整流程

操作：

在左侧 Sidebar 中确认演示案例为“台风导致宁波港停运”，点击“运行完整应急决策流程”。

讲解：

“当前演示案例是台风导致宁波港暂停作业，A供应商发货延误72小时。这里特别说明，初赛 MVP 使用的是模拟数据和专家经验参数，目的是验证流程闭环。”

## 0:35-1:00 解释库存风险

操作：

查看 Step 1“库存监控与风险预警”。

讲解：

“系统首先进行库存监控。核心控制芯片当前库存为3600，小时消耗为100，所以只能支撑36小时。但A类关键客户订单48小时后就要交付，同时A供应商预计延误72小时。因此系统计算出安全库存缺口率、在途延误和库存风险指数，并触发高风险预警。”

强调：

“ChainGuard 的第一点创新是库存监控前置触发，不是等订单延期后再补救，而是在风险指标超过阈值时提前启动应急流程。”

## 1:00-1:35 解释三个 Agent

操作：

查看 Step 3“多 Agent 决策提案”。

讲解：

“接下来系统生成三个 Agent 提案。采购 Agent 建议启用B备用供应商，关注供应替代和供货稳定性。物流 Agent 倾向对受影响订单执行紧急空运，强调运输时效和交付保障。财务 Agent 则反对全量空运，认为应按客户分级保障，因为全量空运可能导致部分订单利润转负。”

强调：

“这里不是单一规则直接给答案，而是让不同业务视角形成多方案对比。”

## 1:35-2:10 解释辩论仲裁

操作：

查看 Step 4、Step 5、Step 6。

讲解：

“系统会先对方案进行评分，并检测冲突。固定案例中，物流方案时效分很高，但成本分较低；财务方案成本控制更强，但时效较弱，因此触发成本-时效冲突。”

“进入辩论过程后，财务 Agent 会反驳物流 Agent 的全量空运方案，指出空运成本过高、可能导致订单利润转负，并建议只对A类关键客户订单空运，非关键订单延期沟通。”

“最后仲裁器输出折中方案：关键订单空运 + 备用供应商补货 + 非关键订单延期沟通。这个方案采纳了采购的备用供应商建议、物流的关键订单空运建议，也采纳了财务的客户分级保障建议，同时拒绝全量空运。”

## 2:10-2:35 解释经验卡片

操作：

查看 Step 7“自学习经验卡片”，点击“保存经验卡片”。

讲解：

“决策结束后，系统会把这次案例沉淀为经验卡片，包括触发条件、失败原因、改进策略、推荐模式和标签。比如本案例的推荐模式是备用供应商 + 关键订单空运 + 非关键订单延期。后续遇到类似台风、港口停运、库存不足的场景，可以通过关键词检索复用这张经验卡片。”

强调：

“这是 ChainGuard 的经验自学习能力，当前用 JSON 和关键词检索实现，未来可以接入 Chroma 做向量检索。”

## 2:35-3:00 说明模拟参数未来可校准

操作：

指向页面底部说明或 Sidebar 参数说明。

讲解：

“最后需要说明，当前 MVP 使用模拟数据和专家经验参数，主要用于验证系统流程闭环。真实企业落地时，可以导入 ERP/WMS/TMS 历史数据，包括库存、订单、供应商、在途物流和历史应急结果，用这些数据校准风险权重、预警阈值和评分规则。”

收尾：

“因此，ChainGuard 当前展示的是一个可运行、可解释、可扩展的供应链应急决策原型。它先用稳定的规则和模拟数据打通闭环，未来可以进一步接入企业数据、Qwen API、Chroma 向量库，并扩展为 FastAPI + Vue 的企业级系统。”
