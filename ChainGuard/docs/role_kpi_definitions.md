# 仓库 / 销售 / 计划三角色 KPI 口径定义

> 状态：**定义草案，本轮不实现**。
> 目的是把 b684f6d 删除的那批伪造 KPI 变成可判定的产品定义，供拍板后再开发。

## 1. 背景：为什么这批 KPI 被删掉

b684f6d 删除了工作台上仓库 / 销售 / 计划三个角色的七个 KPI：

| 角色 | 被删除的 KPI |
|---|---|
| 仓库 | 待执行调拨、今日出入库、盘点差异 |
| 销售 | 待沟通客户、高等级客户风险 |
| 计划 | 受影响工单、待调整计划 |

删除原因不是"没接后端"，而是**系统里不存在对应实体**：没有调拨单模型、没有出入库流水实体表、没有盘点模型、没有工单模型。这些数字当时是写死的字面量。替代方案是三个受行级数据范围约束的真实指标：我的任务 / 逾期任务 / 可见风险数。

要恢复这批 KPI，必须先回答两个产品问题——**"受影响工单"到底指什么**、**"今日"以哪个时区为准**——再评估数据可派生性。本文回答这两个问题并逐项给出可行性结论。

## 2. 先决问题一：「今日」的时区基准

**结论：当前无法实现，缺一个 schema 字段。**

后端全链路使用 UTC（`models.py` 各 `DateTime(timezone=True)` + `utcnow`）。若"今日"直接取 UTC 日历日，对 Asia/Shanghai（UTC+8）的制造企业意味着**每天 08:00 才翻页**——早班 8 小时的出入库会被算进"昨天"，这是用户一眼能看出的错误。

`Tenant` 模型（`src/webapi/models.py:38`）目前字段为 `id / name / industry / scale / status / plan / trial_end_at / demo_data_flag`，**没有时区列**。

实现前置条件：

1. `tenants` 表新增 `timezone`（IANA 名称，如 `Asia/Shanghai`），默认值需明确——建议 `Asia/Shanghai` 而非 `UTC`，与既有演示语境一致；
2. 新租户引导流程（C3）采集该字段；
3. 所有"今日/本周"类聚合按 `tenant.timezone` 求日界，再转回 UTC 查询；
4. 前端展示需与后端同源，不得各自用浏览器本地时区推算。

在这四项完成前，任何带"今日"的 KPI 都不应实现——用 UTC 冒充本地日是新一轮的口径造假。

## 3. 先决问题二:「受影响工单」的定义

**结论：系统里没有"工单"实体。该词需替换为"生产计划行"，且定义需在三个候选口径中选一个。**

系统内最接近"工单"的是 `production_plan` 导入类型，字段（取自 `demo_assets/enterprise/csv/production_plans.csv`）：

```
production_plan_id, plant_warehouse_id, finished_material_id, planned_qty,
planned_start_at, planned_end_at, plan_status, priority,
material_readiness_rate, updated_at
```

`plan_status` 实际取值分布：`planned` 418 / `completed` 849 / `released` 413 / `at_risk` 236 / `paused` 84。

"受影响"的三个候选口径，语义差别很大：

| 候选 | 定义 | 命中量级 | 问题 |
|---|---|---|---|
| A. 自带状态 | `plan_status == 'at_risk'` | 236 | 最省事，但"受影响"完全由导入源判定，系统未做任何推理，KPI 沦为源数据透传 |
| B. 物料齐套率 | `material_readiness_rate < 阈值` 且状态未完成 | 取决于阈值 | 阈值又是一个需要定义的参数，且齐套率同样来自源数据 |
| C. 风险关联 | 计划的 `finished_material_id` 命中当前未关闭风险/事件的受影响物料 | 需实测 | 唯一体现系统自身推理价值的口径，但依赖风险到物料的稳定关联 |

**建议选 C，并在 KPI 旁注明口径**。理由：A/B 本质是把 ERP 已有的字段换个地方显示，而 ChainGuard 对外的价值主张是"关联出企业自己看不到的影响面"。C 也与既有的事件影响面分析（a04）同源，不另立一套关联逻辑。

若选 C，仍需明确：风险的"受影响物料"取自何处（`disruption_events.affected_material_id`？还是影响面分析的传导结果），以及是否只算未关闭的风险。

## 4. 逐项可派生性评估

一个共性约束先行说明：下表中 `inventory_movement` / `production_plan` / `purchase_order` / `shipment` 在导入目录里都是 **`entity: False`**（见 `src/webapi/enterprise_import_catalog.py`），即它们**只以 `ImportSourceRow` 的 JSON payload 形式存在**，没有实体表、没有索引、没有 schema 校验、没有去重与更新路径。基于它们做 KPI 意味着：

- 聚合要在 JSON payload 上做，租户数据量大时无索引可用；
- 源行没有唯一键约束，重复导入会重复计数；
- 字段缺失/类型错误只能在读取时发现。

这与物流页所受的限制完全同源。**任何基于这三类源行的 KPI 都只能定位为"源数据统计"，不能宣称是系统的业务状态。**

### 4.1 仓库角色

| KPI | 数据来源 | 可派生性 | 说明 |
|---|---|---|---|
| 待执行调拨 | — | **不可派生** | `inventory_movements.movement_type` 只有 `transfer_in` / `transfer_out` 两个**已发生**的流水类型，没有"待执行"状态。调拨单是一个带生命周期（待审/待执行/已完成）的单据实体，系统里不存在。需新增调拨单模型与导入链路。 |
| 今日出入库 | `inventory_movement` 源行 | **有条件可派生** | 定义：`movement_at` 落在租户本地当日的行数，`receipt`+`transfer_in` 计入库、`issue`+`transfer_out` 计出库。阻塞于 §2 时区。`quality_hold` / `adjustment` 是否计入需拍板（建议不计，它们不是物理出入库）。 |
| 盘点差异 | — | **不可派生** | `adjustment` 类型的流水是调整结果，不是盘点单。盘点差异需要"账面 vs 实盘"两个数，系统只有调整后的净变动量，反推不出差异。需盘点单模型。 |

### 4.2 销售角色

销售侧是三个角色里数据基础最好的——`customer` 与 `order` / `order_line` 都是 `entity: True`，有真实实体表。

| KPI | 数据来源 | 可派生性 | 说明 |
|---|---|---|---|
| 待沟通客户 | — | **不可派生** | "待沟通"是 CRM 语义（有跟进任务、有未回复工单），系统没有客户沟通记录模型。若强行定义为"有延迟订单的客户"，那它就该叫这个名字，不该叫"待沟通"。 |
| 高等级客户风险 | `customers` + `sales_orders` + 风险 | **可派生** | 建议定义：`customer_level` 为高等级档位、且名下存在未关闭风险关联订单的客户数。两侧都是实体表，可加索引、可行级数据范围约束。这是本批 KPI 里唯一建议直接实现的一项。 |

### 4.3 计划角色

| KPI | 数据来源 | 可派生性 | 说明 |
|---|---|---|---|
| 受影响工单 | `production_plan` 源行 | **有条件可派生** | 术语改为"受影响生产计划"。口径取 §3 的 C 方案。受源行约束（无索引、无去重）。 |
| 待调整计划 | `production_plan` 源行 | **口径不成立** | `plan_status` 里没有"待调整"。最接近的是 `at_risk`(236) + `paused`(84)，但把这两个状态合称"待调整"是发明语义。若要这个 KPI，需要先有"计划调整"这个业务动作及其状态机。 |

## 5. 结论汇总

| 结论 | KPI |
|---|---|
| 建议实现 | 高等级客户风险（销售） |
| 时区问题解决后可实现 | 今日出入库（仓库） |
| 口径拍板后可实现，但受源行限制 | 受影响生产计划（计划） |
| 需新增实体表，本阶段不做 | 待执行调拨、盘点差异（仓库） |
| 口径不成立，不应实现 | 待沟通客户（销售）、待调整计划（计划） |

## 6. 若要推进，建议顺序

1. 拍板 §3 的"受影响"口径（A / B / C）；
2. 给 `tenants` 加 `timezone` 并接入 C3 引导流程——它不只服务本批 KPI，所有"今日/本周"类展示都依赖它；
3. 先实现"高等级客户风险"一项，它数据基础最实、且不引入新的架构债；
4. 其余项按上表分类分别立项，需要新增实体表的部分与导入链路一并设计。

任何一项落地时都需同时确认：行级数据范围（`dept`/`own`/`custom`）如何作用于该聚合，以及无数据时返回 `null` 显示「数据缺失」而非 `0`——这两条是 b684f6d 已经确立的既有约定。
