# ChainGuard 答辩技术详解（从头到尾讲清楚）

> 用途：帮你彻底理解自己的项目——每一步**做什么、用什么公式、为什么这么设计**。
> 所有公式与数字均与当前代码一致（可现场跑出来）。

---

## 0. 一句话总览

> ChainGuard 把"供应链中断应急决策"建模成一个**多目标、强约束的优化问题**：
> 三个部门 Agent（采购/物流/财务）各自从自己的目标出发提方案 → 系统枚举所有组合、在硬约束下求"社会最优"折中 → 历史经验回注影响置信度 → 全过程可解释、可审计、可降级。

**核心数据流（11 步）：**
```
数据层(SQLite/演示场景)
  → Step1 库存风险引擎(4维加权 → 风险指数)
  → Step2 中断事件感知
  → Step3 三 Agent 策略生成(PayoffModel 效用)
  → Step4 评分排序 + 冲突检测
  → Step5 证据驱动辩论
  → Step6 动态仲裁(final_score)
  → Step7 经验卡片生成
  → Step8 约束优化 + 博弈分析(ConstraintSolver/GameAnalyzer → 协调收益)
  → Step9 历史经验检索(TF-IDF) + 参数校准(逻辑回归/事前特征)
  → Step10 LLM 解释(TextGenerator + 模板降级)
  → Step11 审计链(human_approval + JSON 导出)
旁路：HistoryPipeline → TrainingDataset → ModelRegistry(6 模型评测)
```

**一个贯穿全程要记住的原则：** 所有**数值结论由代码计算**，LLM 只负责把结论翻译成人话，绝不改数。这是你抗追问的护身符。

---

## 1. 数据层：决策从哪来

两种输入，走同一套 `DecisionOrchestrator`：
- **演示场景**：固定台风-宁波港案例（`data/*.json`），用于稳定演示，风险指数恒为 70.25。
- **企业场景**：`ScenarioLoader` 从 SQLite 读（`demo_assets/.../chainguard_enterprise_demo.db`，18 表、111,460 行）。选一个中断事件 `event_id`，加载它的库存/供应商/订单/运输上下文。

**为什么这么设计：** "演示场景"保证答辩时输出稳定可控；"企业场景"证明系统不是为台风写死的——换事件，输出真的变（风险 70.25 vs 某事件 19.33）。schema 与真实 ERP/WMS/TMS 对齐 → 企业换上自己的数据即可用。

## 2. Step 1 库存风险引擎

**做什么：** 在断供真正发生前，量化"库存还能撑多久 + 有多紧迫"，决定要不要启动后面的应急决策。

**公式（`inventory_monitor.py`，与代码一致）：**
```
库存风险指数 = 0.35×缺料紧迫度 + 0.25×订单重要度 + 0.20×在途延误风险 + 0.20×外部事件风险
```
四个分量各自归一化到 0–100。演示案例：库存 3600 / 小时消耗 100 → 可支撑 36h；安全库存缺口 2600（缺口率 41.94%）；在途延误 72h；关键订单覆盖率 72% → **风险指数 70.25**，超过阈值 70 → 黄色预警 → 触发应急。

**触发规则：** 可支撑 <48h 黄警 / <24h 红警；覆盖率 <80% 启动客户分级；风险指数 >70 进辩论仲裁。

**为什么这么设计：**
- 用**加权和**而不是 ML：可解释、可审计、专家能看懂每一项贡献——工业客户要的就是"为什么报警"。
- 权重 0.35/0.25/0.20/0.20 是**专家先验**，但不是拍脑袋定死的——Step9 的参数校准会用历史数据给出"建议权重"（见 §10）。这是"专家 + 数据"双轨，比纯专家或纯黑箱都更稳。需要说明的是：**当前演示数据不足以支撑校准**（样本外 AUC 未达标，系统按设计拒绝产出权重），因此线上四个权重仍是专家先验，未被数据改写。

---

## 3. Step 2 中断事件感知

把事件整理成统一的"事件卡片"：事件类型、影响供应商、预计延误、风险等级等，供后面 Agent 推理。复赛支持 5 类：供应商延误 / 物流阻断 / 需求突增 / 质量异常 / 极端天气。**为什么：** 结构化事件是后面所有计算的输入契约，统一格式才能"一套引擎、多种场景"。

---

## 4. Step 3 三 Agent 策略生成（PayoffModel）★核心

**做什么：** 采购/物流/财务三个 Agent，各自有**不同目标**，各出 3 个候选策略，组合成 3×3×3 = **27 个策略组合**。

**关键：每个 Agent 有两套效用（这就是"博弈"的来源）：**
以采购 Agent 为例（`game_model.py`，与代码一致）：
```
own_utility（自私效用）   = coverage_rate×60  + speed_score×0.40
system_utility（社会效用）= coverage_rate×50  + (100/cost_multiplier)×0.50
其中 speed_score = clamp(100 − lead_time/48×50)
```
- **own_utility**：采购只关心"供得上、来得快"，不太管成本。
- **system_utility**：从全局看，既要覆盖率又要成本效率。

**为什么这是博弈而不是简单评分：** 因为**每个 Agent 自私最优的选择，和全局最优的选择往往不一样**。采购想加急（快但贵），财务想控本（便宜但慢）——它们的 own_utility 指向不同策略。这种"个体理性 ≠ 集体最优"的张力，就是博弈的本质，也是后面"协调收益"的来源。

**为什么不是固定模板（vs 初赛）：** 初赛的分数是写死的常量；现在每个分数都由 `available_qty / lead_time / cost_multiplier` 等**输入字段算出来**——换数据，分数和排序就变。这是"真多智能体"和"三个模板"的根本区别。

---

## 5. Step 4 评分排序 + 冲突检测

**total_score 公式（`scoring.py`，权重来自 config）：**
```
total_score = 0.25×时效 + 0.20×成本 + 0.25×风险降低 + 0.20×可行性 + 0.10×服务保障
```
按 total_score 排序得到方案排名。

**冲突检测：** 最高分与最低分**分差 > 15**，或目标方向相反（如成本 vs 时效），即判定"有冲突" → 触发辩论。

**为什么：** 五维加权 = 把"成本-时效-风险"的多目标压成一个可比较的标量，便于排序；但压成标量会**藏住冲突**，所以再用分差/方向单独把冲突**显式暴露**出来——这正是 Step5 辩论的入口。

---

## 6. Step 5 证据驱动辩论

**做什么：** 低分 Agent 反驳高分方案，指出它的成本/风险/执行漏洞。

**关键改进（vs 初赛）：** 分支条件从"中文关键词匹配"改成**读结构化参数**：
- 旧：`if "全量空运" in text`（脆弱、可笑）
- 新：`if scores["cost"] < 40`（高成本运输）、`if scores["timeliness"] < 75`（偏保守）、`if supplier_ids 数量 ≤ 1`（缺备用供应商）

**为什么：** 评委一旦发现你的"辩论"是在 grep 中文字符串，整个"证据驱动"的说法就崩了。改成读分数/字段后，辩论是真的基于结构化证据，且换语言、换场景都成立。

---

## 7. Step 6 动态仲裁（final_score）

**final_score 公式（`arbitrator.py`，与代码一致）：**
```
final_score = min(100, 最高分提案 + 反驳加分 − 冲突惩罚)
  反驳加分 = +4（若辩论产生了修订建议 suggested_revision）
  冲突惩罚 = −2（若检测到冲突 has_conflict）
```
仲裁结论的标题、执行计划、预期效果由 `context` 与 `event_type` **动态生成**（不是写死台风话术）。

**为什么 +4/−2 这种简单加减：** 因为这一步要的是**可逐项推导、可在 PPT 上写清楚**的分数演化（"最高分81.6 +4 −2 = 83.6"），而不是又一个黑箱。可解释 > 复杂。

---

## 8. Step 7 经验卡片生成

把本次决策（尤其低分/失败的）沉淀为"经验卡片"：触发条件、推荐模式、失败原因。**为什么：** 这是自学习闭环的"写入端"——决策不只是用完就扔，而是变成下次可检索的资产。

---

## 9. Step 8 约束优化 + 博弈分析（ConstraintSolver / GameAnalyzer）★核心

**ConstraintSolver（`constraint_solver.py`，与代码一致）：**
- 枚举 27 个组合，对每个算 `combined_system_utility = Σ agent_i 的 system_utility`。
- **硬约束**：供给覆盖率 ≥ 0.30、交期 ≤ 72h、成本倍数 ≤ 5。
- `individual_system_utility`：每个 Agent 各选**自己 own_utility 最高**的策略（自私组合）的系统效用。
- `optimal_system_utility`：所有**可行**组合里系统效用最高的。
- 若无可行解 → 返回"最小违约的最优不可行解" + 未满足约束（不崩）。

**GameAnalyzer：** 把"自私最优 vs 约束社会最优"显式对比：
```
协调收益 = optimal − individual = 195.50 − 183.09 = +12.41（+6.8%）
```

**为什么这是全场最值钱的一块：**
- 它用一个**可复现的数字**回答了"你的多智能体到底有没有用"——如果各部门各自为政（自私最优）系统效用 183.09，协调后 195.50，**协调本身值 +12.41**。这就是"1+1>2"的量化证据。
- 硬约束保证方案**不超供给/不超期/不超预算**——是"优化"而不是"瞎选"。
- 详见 §下面的纳什均衡讨论：这个 `individual`（自私组合）就是"非合作博弈的自私稳定点"，约束社会最优正是**协调地偏离它**。

## 10. Step 9 历史经验检索 + 参数校准 ★自学习核心

**经验检索（TF-IDF）：**
- 600 条历史决策 → 606 张经验卡片（语料库）。
- 用 TF-IDF 把当前场景和历史卡片做相似度匹配，召回最相似的几条。
- 每条给出 `confidence_adjustment`（+0~0.3）和 `risk_hints`，**注入到每个 Agent 方案的 `experience_hints` 字段**。

**参数校准（事前特征 + 逻辑回归 + 样本外验证）：**

按决策时点重建四个**事前**因子（可支撑时长、关键订单覆盖、**预计**到货延误、事件强度），
对成败标签做带 L2 正则的逻辑回归，用系数定权重；分层切分训练/测试，报样本外 AUC 与 Brier，
并与专家权重在**同一测试集**上对比排序能力。触发阈值按**期望代价最小**选取（漏报:误报可配），
不再取失败样本分位数——只优化召回会造成告警疲劳。

**校准不成立时明确拒绝，不产出权重**，判据：
有效样本 ≥ 80 且正负类各 ≥ 40；至少一个因子系数为正；样本外 AUC ≥ 0.55。
未通过验证的权重**不允许写入租户配置**（后端返回 CG-2902）。

> **早期版本用的是"归一化皮尔逊相关"，已废弃。** 那一版直接拿
> `covered_demand_rate` / `lost_orders` / `actual_delay_hours` / `production_downtime_hours`
> 当特征——它们全是事后结果，而标签 `outcome_status` 正是由这些量算出来的，
> 构成目标泄漏；且取绝对值丢掉方向、边际相关不处理共线性。
> 那一版曾对外给出的"0.35→0.287、0.25→0.446"等数字**不再作为结论引用**。
> 两代方法的并排对比可现场复跑：`python scripts/diagnose_calibration.py`。

**当前演示数据的诚实结论：** 企业演示数据包的 `outcome_status` 由一个随机隐变量生成
（见 `scripts/generate_enterprise_demo_data.py` 的 `latent_quality`），与库存状态无因果关系，
因此新方法在该数据上**样本外 AUC ≈ 0.47，正确地拒绝校准**，线上继续使用专家先验。
诊断脚本同时跑一份植入已知权重的对照数据，证明估计器本身能还原真实权重（AUC ≈ 0.80）——
即"拒绝"是数据没信号，不是算法坏了。

- **只输出建议、人工审批后才更新 config**，不自动覆盖；批准时把样本量、方法、
  样本外 AUC、批准人与时间一并写入配置，事后可完整追溯。

**为什么这么设计（也是抗追问要点）：**
- "自学习改了哪个决策变量"——答案是 `confidence_adjustment` 注入了每个方案，以及参数校准给出的权重建议。**具体、可指。**
- 为什么不让历史经验直接覆盖决策？因为**坏的历史经验会污染当前决策**——所以经验只作"特征/证据"，不作"硬覆盖"；校准只作"建议"，要人工审批。这是负责任的自学习边界。
- 为什么 TF-IDF 而不是大模型 embedding？600 条规模 TF-IDF 完全够、且**离线可跑**；embedding 作为可选增强（无模型时自动降级回 TF-IDF）。

## 11. Step 10 LLM 解释（TextGenerator）

**做什么：** 在线时调 Qwen2.5/Ollama 生成流畅的仲裁摘要、辩论叙述、经验卡片文本；**离线/失败时自动降级为完全数据驱动的模板**（无任何演示专用词）。

**安全边界（必背）：** LLM 只把"代码算好的结论"翻译成人话，**所有数值和硬约束判断都由代码生成，LLM 不得修改**。页面也明确区分"算法结论"和"AI 生成解释"。

**为什么：** 大模型会幻觉。把它关在"只解释、不决策"的笼子里，既享受表达流畅，又不让它污染数值——这是用 LLM 做严肃决策系统的正确姿势。

---

## 12. Step 11 审计链

每次决策生成审计记录：`decision_id / scenario_type / optimal_combo / constraint_analysis / experience_confidence / human_approval_required / decision_status`，一键导出 JSON；成本高于阈值强制 `human_approval_required=True`。**为什么：** 工业决策要追责。可审计 + 人工审批 = 系统是"决策辅助"而非"替人背锅"，这是落地的合规前提。

## 13. 旁路：训练与评估（6 模型 + ModelRegistry）

**做什么：** 从 600 条历史决策提 5 个特征（覆盖需求率、延误比、成本比、停工归一化、人工评分归一化），预测决策成败状态（success/partial/failed），对比 6 个模型，按 **F1-macro** 选型并经 ModelRegistry 注册稳定版本。

**真实结果：** Prior(基线) acc0.60/f1 0.25 → DecisionTree acc0.72/**f1 0.712（最优）**、RandomForest 0.72/0.711、Logistic 0.60/0.65、NB 0.64/0.62、SVM 0.60/0.63。

**为什么按 F1-macro 而不是 accuracy 选型（关键抗追问）：** 三类**不平衡**（success 337 / partial 152 / failed 111），accuracy 会被多数类拉高；F1-macro 对每一类平等加权，更公允。

> ⚠ **这个 0.712 不是"预测能力"，已实测确认。** 该口径的 5 个特征（覆盖需求率、延误比、
> 成本比、停工归一化、人工评分归一化）全是**事后结果**，而标签 `outcome_status` 正是由这几个量
> 经 `derive_outcome_quality` 算出来的——模型学到的是生成器的那条确定性映射，属于目标泄漏，
> 与 §10 早期校准方法同源。
>
> **换成事前特征重跑（同一批 600 条、同样 6 个模型）：最优 f1-macro 从 0.712 掉到 0.284**，
> 而多数类基线（PriorClassifier）就有 0.246 —— 相对基线几乎没有提升，
> 与 §10 校准得到的样本外 AUC ≈ 0.47 完全一致：**这份数据里不存在"事前可预判成败"的信号**。
>
> 因此诚实口径是：**"能从结果指标复原结果标签"（0.712），不是"能提前预判决策成败"（0.284）**。
> 代码中两套特征已显式区分为 `POST_HOC_FEATURE_NAMES` 与 `PRE_EVENT_FEATURE_NAMES`，
> 结论由 `tests/test_supervised_calibration.py::test_pre_event_model_comparison_is_far_weaker_than_leaky_one` 锁定。
**定位话术：** 这个预测是**辅助模块**，主线决策（效用+约束求解）不依赖它——别让评委盯着 0.72 当主菜打。

## 14. 工程化（复赛后增强，落地可行性）

- **REST + 细粒度 RBAC**：FastAPI `/api/v1` 以 JWT 绑定用户、租户、角色与数据范围，按操作权限校验，越权 403。
- **数据安全**：按角色字段级脱敏 + 敏感数据可选静态加密 + TLS 文档。
- **多租户**：租户身份来自已验证 JWT 与持久化用户，业务查询按租户和数据范围隔离。
- **ERP 连接器**：抽象 + REST 适配器，从 ERP 拉事件→决策→回写，已对 Mock ERP 端到端验证。
- **存储后端**：默认 SQLite、可选 PostgreSQL（连接工厂 + 迁移脚本）。
- **可观测性**：结构化日志 + 服务 JWT 保护的 `/metrics` + `/healthz`/`/readyz` 探针。
- **质量**：308 项单元测试，覆盖正常/边界/失败/全降级路径。

**为什么这些重要：** 它们把项目从"Streamlit demo"推向"能进企业采购流程的产品"——直接加"落地可行性"的分。

## 15. 三条贯穿全局的设计哲学（被问"你整体怎么想的"就答这个）

1. **数值由代码、表达由 LLM**：决策可信的前提是可回溯，所以硬约束/数值全在代码，LLM 只润色。
2. **专家先验 + 数据校准双轨**：纯专家拍板不可信、纯黑箱不可解释——两者结合，且数据只给"建议"、人工把关。
3. **能力可证明、可降级、可审计**：每个能力都有测试证明、有离线降级、有审计留痕——不夸大任何一个 Mock 或规划。
